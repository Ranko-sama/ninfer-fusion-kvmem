实验方法
两次独立服务进程，顺序相同，使用原始请求文件的相同字节。固定请求序列来自
archive/20261014-before-rollback/benchmarks/decode-next-20261013/performance/04-old，
即历史非法 token 故障所在序列：warmup、short-decode、long-first、long-followup、
long-decode。原种子、采样参数、每请求输出上限均保留，没有人工改写历史答案。
两次使用独立 LOCALAPPDATA 运行缓存，清除继承的 NINFER_*，显式设置原冻结 profile
与 NINFER_PREFILL_ALIGN=0。当前 q5 profile 的 60 个 routed keys 在启动日志确认载入。
实际 engine 与 sampling_defaults 相等，五组实际 request 日志也全部相等。

默认配置仍为当前 q5 冻结配置：同一模型，RK8V4、FP16 GDN、MTP4、chunk384、
上下文/KV 102400、并发1、host KV0、device state0、shared prefix0、ngram0、
CUDA Graph allowance128MiB，temperature1、top_p.95、top_k20、xhigh、默认输出94208。
本轮复用的历史请求显式输出上限为64/2048/4096/4096/2048，不改变服务默认上限。
这验证的是原包在当前冻结配置下的表现，不是第三方旧 BAT 自带默认配置的重演。
模型17.8GB文件的大小和mtime与既有SHA记录一致，本轮没有再次全文件重算模型SHA。

因果边界
1. 我们的适配、后续性能优化和新增诊断插桩，不是这次可见输出分叉的必要条件。
   因而整体回退到这个第三方原包，也不能满足当前“同种子输出一致”的验收条件。
2. 最早出现分叉的 long-first 两次 cached_tokens 都为0；此前warmup及short-decode
   的可见输出完全相同。分叉不需要先发生不同的可见对话，但long-first并非冷启动
   的第一个请求，因此本轮没有排除跨请求内部状态，也没有捕获其首次数值差异。
3. 原包没有内部张量或实际token-ID完整捕获；不能证明它与q5已捕获的有限张量分叉
   或历史NaN有相同根因，不能用最终正文一致来替代内部数值正确性。
4. 尚未取得原包的第三方SM75改动源码，且它使用CUDA13，q5使用CUDA12。这里是原包
   整体的复现证据，无法继续区分纯上游、第三方适配、CUDA环境或模型的责任。
5. 非法token在这2轮内未复现，是有上限的阴性结果；不等于历史问题消失或被修复。

投入与停止
预定最多2次冷启动、10个请求、模型实验20分钟；启动120秒、每请求420秒上限，
出现错误/超时/身份不符即停止整个实验，无重试、无编译、无插桩、无性能专项测试。
实际2次冷启动、10/10个请求完成，约630.31秒（10分30秒）；两个自有服务均退出，
3683/3684端口已释放。plan.json已关闭且禁止追加运行，不做第三轮碰运气。
本轮没有修复根因，也没有能力验收结论。保留发布阻断，停止继续向更早包盲目回退。
若后续另立任务，应只围绕已有具体证据设立新的有界判定；不得自动续跑旧计划。
